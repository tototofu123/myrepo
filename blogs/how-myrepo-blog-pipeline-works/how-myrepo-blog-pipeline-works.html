How myrepo's Perplexity → GitHub → Pages Blog Pipeline Works

A deep-dive into the automated pipeline that turns a Perplexity chat message into a live, styled blog post on GitHub Pages — no manual deployment needed.

Overview

Every post on this blog starts life as a single sentence in a Perplexity chat window. No Git commands. No local editor. No manual deploys. This post explains the four-layer system that makes that possible — and how each layer hands off to the next.

Layer 1 — The Perplexity Skill

The skill lives at .perplexity/skills/create-blog.md inside the repo. Every time a session starts, Perplexity reads skill files it is given access to, so when you say "create a blog about X", it already knows what to do:

  1. Collect title, slug, summary, tags, and content (asking you only for what's missing)
  2. Format everything into a structured Markdown block using a strict frontmatter template
  3. Save a Markdown draft into Notion /Blogs// and wait for your approval
  4. Only after you say "publish this blog" — create a GitHub Issue titled [blog] with the label blog

The skill is just a Markdown file — updating it is as simple as editing .perplexity/skills/create-blog.md in the repo. No code changes, no redeployment.

Layer 2 — The GitHub Issue as a Data Container

GitHub Issues are the pipeline's message bus. The body carries all the data the workflow needs:

FieldWhere it livesExample
titleYAML frontmatter"How myrepo Works"
slugYAML frontmatter"how-myrepo-works"
dateYAML frontmatter"2026-05-23"
tagsYAML frontmatter[automation, github]
Post contentAfter the --- blockFull Markdown prose

Using issues gives you a built-in human verification step — only adding the blog label triggers the workflow. Labelling is the "go" signal.

Layer 3 — GitHub Actions Workflow

The workflow file lives at .github/workflows/create-blog-post.yml. It fires on:

on:

  issues:


    types: [opened, labeled]

Steps in order:

  1. checkout — clone the repo at HEAD
  2. setup-node — install Node 20
  3. npm ci — install dependencies (marked, gray-matter)
  4. node .github/scripts/generate-blog.js — parse issue body → write public/blogs//.html and public/blogs//convert.json
  5. Commit + push the new files to main
  6. peaceiris/actions-gh-pages — copy public/ to the gh-pages branch
  7. Bot comments on the issue with the live URL, then closes it

Total time from issue creation to live post: ~90 seconds.

Layer 4 — The Generator Script

.github/scripts/generate-blog.js does three things:

1. Parse the issue body

It uses gray-matter to split YAML frontmatter from Markdown content:

const { data: meta, content } = matter(issueBody);

// meta.title, meta.slug, meta.date, meta.tags


// content = the Markdown post body

2. Convert Markdown → HTML

It uses marked with GFM support (tables, strikethrough, task lists, fenced code blocks):

const html = marked.parse(content, { gfm: true, breaks: true });

3. Inject into a styled HTML shell

The script wraps the HTML in a full page template with:

  • Instrument Serif (display font) + Work Sans (body font) from Google Fonts
  • CSS variables for light/dark theming (prefers-color-scheme + manual toggle)
  • Scroll-reveal animations via IntersectionObserver
  • Syntax highlighting for code blocks
  • Responsive layout capped at 720px
  • Output written to public/blogs//.html
  • Shared styles referenced from public/blogs/blog-styles.css
  • Conversion spec written to public/blogs//convert.json
